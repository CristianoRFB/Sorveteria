1. ESTÁGIO ATUAL DO PROJETO
======================================================================

Este é um projeto NOVO.

A estratégia inicial é:

1. estudar a melhor base disponível do projeto de Açaí + Sabor;
2. identificar o que é realmente reutilizável;
3. separar lógica genérica de lógica específica de açaiteria;
4. adaptar os módulos reaproveitáveis ao domínio de sorveteria;
5. transformar a solução desde o início em SaaS multi-tenant white-label;
6. utilizar a Sorveteria Sol de Verão, de Santa Fé do Sul/SP, como caso comercial e tenant de referência;
7. não inventar dados reais da Sorveteria Sol de Verão que não tenham sido confirmados;
8. manter o produto reutilizável para muitas sorveterias.

O projeto NÃO deve nascer single-tenant para depois ser convertido.

A tenancy deve ser uma decisão estrutural desde o começo.

======================================================================
9. DRIVER — ENTREGADOR
======================================================================

DRIVER é o entregador.

O entregador deve possuir uma experiência extremamente simples, mobile-first.

Ele deve acessar apenas o necessário para realizar suas entregas.

Pode visualizar, conforme autorização:

- entregas atribuídas a ele;
- código do pedido/entrega;
- nome necessário do cliente;
- telefone necessário para contato;
- endereço de entrega;
- observações de entrega;
- valor a receber, se pagamento for na entrega;
- forma de pagamento;
- troco solicitado;
- horário de saída;
- estimativa;
- rota/mapa;
- status da entrega.

Ações possíveis:

- aceitar/assumir entrega quando o fluxo permitir;
- marcar “saí para entrega”;
- abrir rota;
- marcar “cheguei”;
- solicitar código de confirmação;
- inserir código;
- confirmar entrega;
- registrar problema;
- registrar tentativa de entrega;
- devolver pedido ao estabelecimento quando necessário.

O entregador NÃO deve:

- acessar financeiro geral;
- editar preços;
- editar catálogo;
- acessar clientes que não estejam relacionados às suas entregas;
- alterar configurações;
- acessar outros tenants;
- visualizar pedidos não atribuídos, salvo regra operacional explícita.


======================================================================
10. CÓDIGO DE ENTREGA
======================================================================

A entrega deve possuir confirmação por código.

Não confundir:

CÓDIGO PÚBLICO DO PEDIDO
com
CÓDIGO DE CONFIRMAÇÃO DA ENTREGA.

Preferir entidades/valores separados.

Fluxo conceitual:

PEDIDO
→ PREPARO
→ PRONTO
→ ATRIBUÍDO AO ENTREGADOR
→ SAIU PARA ENTREGA
→ CHEGOU
→ CLIENTE INFORMA O CÓDIGO DE ENTREGA
→ DRIVER INSERE O CÓDIGO
→ SISTEMA VALIDA
→ ENTREGA CONCLUÍDA.

O código de entrega deve:

- ser curto o suficiente para uso humano;
- não ser sequencial trivial;
- não expor dados internos;
- ser associado ao pedido correto;
- possuir uso único;
- deixar de ser válido após entrega/cancelamento;
- possuir proteção contra tentativas abusivas;
- nunca ser utilizado como credencial administrativa.

O cliente precisa ser orientado:

“Guarde este código. Ele será solicitado pelo entregador para confirmar a entrega.”

O entregador deve ter uma tela clara para inserir/validar o código.

O Admin/Tenant Owner pode possuir mecanismo explícito de override de entrega para exceções, sempre auditado.


======================================================================
11. ACOMPANHAMENTO DO PEDIDO
======================================================================

O cliente deve conseguir consultar o pedido.

Status conceitual adaptável:

RECEBIDO
→ CONFIRMADO
→ EM PREPARO
→ PRONTO
→ AGUARDANDO ENTREGADOR
→ SAIU PARA ENTREGA
→ ENTREGUE.

Também:

CANCELADO.

Para retirada:

RECEBIDO
→ CONFIRMADO
→ EM PREPARO
→ PRONTO PARA RETIRADA
→ RETIRADO.

Não mostrar etapas irrelevantes para o modo de fulfillment.

O sistema deve fornecer:

- status;
- timeline;
- estimativa;
- código público do pedido;
- modo entrega/retirada;
- última atualização.

Quando possível, usar realtime via Firestore listener sem polling agressivo.

14. FIREBASE É A BASE PADRÃO
======================================================================

Por padrão, este projeto deve utilizar Firebase.

Avaliar e utilizar conforme necessidade:

- Firebase Authentication;
- Cloud Firestore;
- Firebase Storage;
- Firestore Security Rules;
- Storage Rules;
- Firestore Indexes;
- Emulator Suite;
- Firebase App Check;
- Firebase Functions apenas quando necessárias;
- Firebase Cloud Messaging quando realmente útil;
- Admin SDK apenas em ambiente confiável.

A multi-tenancy padrão é EM NÍVEL DE APLICAÇÃO.

Não exigir Google Cloud Identity Platform Multi-Tenancy sem motivo.

Conceitos obrigatórios:

- tenantId;
- memberships;
- roles;
- ownership;
- Security Rules;
- isolamento;
- validação;
- audit logs.

Não criar um Firebase por tenant por padrão.

28. SEGURANÇA MULTI-TENANT
======================================================================

Esta é uma exigência estrutural.

Provar:

- tenant A não lê tenant B;
- tenant A não escreve tenant B;
- customer A não lê customer B;
- driver A não acessa entregas de outro tenant;
- driver não vê pedido não atribuído sem permissão;
- usuário sem membership não acessa tenant panel;
- alteração de slug não concede acesso;
- alteração manual de tenantId não concede acesso;
- owner não vira Platform Admin;
- cliente não altera preço;
- cliente não confirma pagamento privilegiado;
- uploads são tenant-scoped;
- caches não vazam tenant;
- logs não vazam secrets;
- Platform Admin possui acesso global explicitamente autorizado.

Se usar Admin SDK:

não depender de Security Rules para operações server-side.

Validar autorização explicitamente.
